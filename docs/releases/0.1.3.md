Sonoskope 0.1.3 adds automatic microphone-level monitoring.

## What's changed

- New **Automatically monitor microphone levels** setting, off by default. After opt-in and microphone authorization, capture follows input devices used by other apps and stops when they release input. The preference is remembered.
- Live input dBFS and a purple microphone trace continue beyond the manual test's ten-second limit.
- Sonoskope excludes its own capture activity so it cannot keep the microphone open indefinitely. Two-second polling plus a two-second idle grace normally stops capture within about 2–4 seconds of external input ending.
- Supports an observed non-default input. Multiple active inputs use the current active target or active system default; ambiguous or unknown usage does not trigger capture.
- Pause, sleep, demos, permission loss, device changes and explicit disable stop or re-evaluate capture. Late callbacks are rejected; capture failures and missing data retry with a backoff.
- Keeps the explicit ten-second test when automatic monitoring is off.
- Input curves identify apps using the monitored microphone. Select an earlier time to inspect its original app labels; concurrent input apps are listed together. Labels indicate shared device usage, not independent app volumes.
- Explicit input and output device names, with active capture distinguished from the system default route. Built-in microphones, speakers, USB audio and headsets use the same monitoring paths.
- Input fault evidence is separated by microphone identity, preventing gaps from different microphones from accumulating into a false incident.
- Updated English/Chinese UI, permission descriptions, and README files.

## Validation and limits

63 automated tests cover diagnosis, localization, automatic input policy and application lifecycle. Lifecycle tests use an injected microphone and do not open physical input devices. The app is also checked after relocation for bundled translations. The user confirmed continuous real input curves with Voice Memos. Physical stop timing, built-in input capture, Teams behavior, non-default input hardware, Bluetooth mode changes and long-call impact still require acceptance testing; see `docs/automatic-input.md` and `docs/validation.md`.

Input IO activity is not speech detection or meeting mute state. A muted meeting may keep input active. Opening a microphone can affect Bluetooth mode. Metrics describe local input, not what remote participants hear. Raw audio is never saved or uploaded.
